# Base UI fidelity audit

fluidfunctionalism's `registry/base/*` (0a0377e) is built on `@base-ui/react` 1.9.0 (`package-lock.json`). This port
rebuilds that behaviour by hand in Solid on gpuix. Each table compares one primitive's behaviour, limited to the parts
and props FF uses (defaults included), against Base UI 1.9.0's source and this port.

- Base UI refs are relative to `packages/react/src/` of mui/base-ui at `v1.9.0`; port refs are relative to this
  directory; FF refs are to `registry/base/*` unless stated.
- Status: **ported** (same behaviour), **gap** (fixable in the port), **fixed (sha)** (was a gap, fixed here),
  **blocked by gpuix** (gpuix still lacks the capability; the note cites the FORK.md line or the probe that shows it), **n/a** (FF overrides it, or out of scope). A gpuix capability the port has not adopted yet is a **gap**, and the note names the API to use.
- Where Base UI and FF disagree, the port follows FF; each section lists those conflicts.

## Summary

About 175 gaps were fixed on this branch (Status `fixed (sha)`), and the gpuix DOM-parity release removed most of what blocked the port: DOM click and pointer semantics, explicit pointer capture, hover and wheel chaining, ARIA and `inert`, forms, popup flip and anchor width, outside press. What is left:

- **Not fixed in the port, no gpuix cause**: mount-order indices for accordion items and tabs (static lists only), tabs-subtle
  horizontal overflow (no demo overflows), and FF-only layers that are not Base UI (select gap-click, combobox `onCreate` / `variant` / `error` / `size`, tabs `selectedIndex` / `onSelect`, button `active` /
  `asChild`). DirectionProvider / RTL is deliberately not ported: FF's docs never mount a provider and gpuix has no
  RTL layout.
- **Gap, gpuix now has the API and the port has not adopted it**, grouped by the API to use:

| gpuix API | Rows left as `gap` |
|---|---|
| Pointer events that no longer capture or hide the ancestor: `onMouseMove` on a trigger keeps the child's click, enter and leave fire per element (FORK.md:296, :351, :406) | switch hover count |
| `maskImage` (host.ts:575), `onScroll` offsets, rounded overflow clip (FORK.md:32) | scroll fade and thumb inside select / combobox popups (the `ScrollArea` fade, dividers and rounded clip are done) |
| Motion: `pathLength` / `strokeDasharray` (host.ts:276-297), colour transitions (FORK.md:33), `createMotionValue` / `createSpring` (packages/solid/src/index.ts:36-38) | switch drag from the live thumb |
| `display: contents` (FORK.md:564) | menu `RadioGroup` `role="group"` wrapper |
| `<input disabled>` (FORK.md:451) | combobox `disabled` (still `readOnly` + `tabIndex` -1) |
| `position: absolute` against the nearest positioned ancestor (FORK.md:559) | dialog `container` (still the direct-child `scoped` placement) |

- **Blocked by gpuix**, only what gpuix still lacks:

| gpuix lacks | Hits |
|---|---|
| CSS `transform` scale and rotate: quads, shadows and hitboxes carry no matrix (FORK.md:876-885, "Not built: size morphs, scale and rotate") | select / combobox popup `scaleY` entrance |
| Pointer position over empty space: events are emitted only for types some element on the hit path listens to (FORK.md:292), and the probe found `window` / `document` `mousemove` listeners fire only then, never over bare window background | exact safe polygon (tooltip, menu submenu) |
| `<input type="range">`: `InputType` has no `range` (packages/native/js/host.ts:1175) | slider native range input under each thumb |

Harness note: the test renderer's `press` sends key-down only (no key-up), so Space-on-key-up (switch) and a held
Space were checked with a temporary native script, not a committed scenario; `style.active` does not show for a
held Space.

## Group notes (disclosure: Accordion, Collapsible, Tabs, Button)

- Base UI 1.9.0 Accordion has **no roving arrow / Home / End navigation**: `orientation` and `loopFocus` are deprecated no-ops (`accordion/root/AccordionRoot.tsx:143-148, 188-194, 207-215`), no `accordion/*` file handles a navigation key, and the trigger is a plain `useButton` tab stop. The brief's accordion keyboard list does not exist in the source. The port's Up/Down/Home/End is an extra that matches the Radix registry variant (see conflicts).
- The port measures with gpuix's `onLayout` (border-box size, reported after the first paint and on every size change, not on pure moves): `src/lib/measured-height.ts` (accordion, thinking-steps, sidebar, input-message, ask-user-questions), the slider track and row, tabs-subtle's label width and the scroll area. A box that moves without resizing is read with `getBoundingClientRect` at the moment it is needed, and fluid hover follows a `ResizeObserver` (`src/lib/fluid-hover.ts:125`); the retry timers, `awaitBounds` and `remeasureFor` are gone (0441497).
- Verified in the harness before fixing: from a cold start Tab never reached an accordion trigger (it alternated between two other stops), and with a `ThinkingSteps` closed Tab landed on its nested `ThinkingStepDetails` trigger. Both fixed. gpuix now has `display: none` and `display: contents` (FORK.md:564), but closed panels still do not use them: the accordion unmounts its text after the exit (`src/components/accordion.tsx:535-600`) and thinking-steps marks a closed panel `inert` (`src/components/thinking-steps.tsx:205-207`).
- Held Space: with a `buttonProps` button focused, the frame while Space is down is pixel-identical to the frame while another key is down (focus ring only) and differs from a pointer press, so `style.active` does not show for a held Space. Recorded in `drift/button.md`. `simulateKeystrokes("space")` also delivers no key-up to elements (explicit `nativeSimulateKeyDown` + `nativeSimulateKeyUp` does), so scenarios use Enter.
- Probes at the current gpuix: the bounds of a child agree with its ancestor's while the ancestor moves, a padded scroller no longer counts its padding twice, `Show` / `For` no longer leave a gap slot, `relatedTarget` is present on focus events, and `IntersectionObserver` fires when a target moves without resizing.

### FF-vs-Base-UI conflicts

- The FF docs pages import the **Radix** registry (`app/docs/accordion/page.tsx:9`, `tabs/page.tsx:5`, `button/page.tsx:5`), not `registry/base`. What the site shows for keyboard (accordion Up/Down/Home/End, Radix tab roving that skips disabled tabs) is Radix behaviour. Base UI 1.9.0 accordion has no arrow nav; the docs text "keyboard navigation" (`app/docs/accordion/page.tsx:48, 196`) describes the Radix build. FF shows nav, so the port keeping it is right.
- `collapsible` is documented and used in FF snippets (`app/docs/accordion/page.tsx:18, 29`) but Base UI single mode is always collapsible (FF says so at accordion.tsx:520). Port omits the prop: same behaviour.
- A disabled accordion item gets no dim in FF (see table).

### Open judgement calls

- (settled by lead) Keep the port's accordion arrow nav (matches the live Radix site, absent from Base UI 1.9.0)? Recommend keep, but add the tab stop fix first, since without it keyboard users cannot reach the group.
- Disabled item visuals: FF draws none. Dimming is arguably better, but it is a deviation.

### FF-vs-Base-UI conflicts
- Stacked range thumbs: Base UI's `Control` gives the press to the last of equidistant thumbs (`slider/control/SliderControl.tsx:251-257`, `<=`); FF gives it to thumb 0 (`slider.tsx:694`). Port follows FF (`src/components/slider.tsx:539-544`).

- In `steps` mode the primitive's values are list indices, so Shift/PageUp/PageDown step through list entries (10 at a time), and `aria-valuenow` is an index (FF compensates with `getAriaValueText`).
- FF's `onChange` sees the Base UI keyboard value unrounded for PageUp/Down (see the PageUp row), so with `step` 25 the value can be off-grid (50 to 60), which pointer input can never produce.

- Whether to replicate Base UI's off-grid PageUp (value + 10 regardless of `step`) or keep the port's step-multiple. I recommend matching Base UI/FF exactly, since FF ships that.
- Whether range thumbs should announce "start range"/"end range" in `aria-valuetext`. Settled (046a443): the port emits `"N start range"` / `"N end range"` when `isRange`.
- The compact engine props `hideFill`, `thumbColor`, `thumbBorderColor`, `trackClassName`, `trackStyle`, `fillClassName`, `fillStyle` (FF `slider.tsx:78-84`) are not ported at all; out of Base UI scope but a fidelity gap in the public API.

### FF-vs-Base-UI conflicts

- **Inline panel is not a menu.** FF's `Dropdown` is `role="group"` with plain divs (`registry/base/dropdown.tsx:83-92,185`), only the popup `DropdownContent` is a Base UI `role="menu"`. Port follows (`dropdown.tsx:657`).
- **`closeOnClick`.** Base UI radio and checkbox items default to `false`; FF forces `true` for single selection and `false` for `checkedIndices` (`registry/default/menu-item.tsx:292`). Port follows FF.
- **Pointer open.** Base UI highlights nothing and focuses the popup on a pointer open; FF's two-frame effect then focuses the first enabled row (`registry/base/dropdown.tsx:455-482`), so every non-submenu open starts ready to act. The port follows FF: panel first, first row 32 ms later (`dropdown.tsx:504-545`).
- **Search field joins the arrow ring.** Base UI would loop the rows only (or use virtual focus via `Menu.Input`/filter parts, which FF does not use); FF makes the field one stop, with arrows leaving it for the first/last row and coming back past either end (`dropdown-search.tsx:128-131`). Port follows FF (`dropdown.tsx:331-353`), with real focus on the field and on the rows.
- **Submenu side is physical.** FF reads `useDirection()` and passes `side="left" | "right"` rather than `inline-end` so its `data-side` enter choreography works (`registry/base/dropdown.tsx:865-889`). Port uses `side="right"` always.
- **Stale comment in FF.** `registry/default/menu-item.tsx:55-57` and `registry/base/dropdown.tsx:536-539` say Base UI's Enter/Space "dispatch no DOM click". In 1.9.0 they do: `useButton.ts:138-152,172-175` calls `dispatchClickWithModifiers`. FF's `onClick`-on-the-primitive wiring works either way, so no port impact.
- **Hover highlight is FF's.** The sliding highlight is `useFluidHover` (nearest row, gap clicks routed to the lit row via `handlers.onClick`, `registry/base/dropdown.tsx:667`), not Base UI's item hover; Base UI's hover-to-focus sync still runs underneath. Port has the fluid hover but not the gap click (README "Not ported").
- **FF docs use options the port lacks.** `app/docs/sidebar/page.tsx:426` shows `DropdownContent side="top" sideOffset={6}`; the dropdown docs page itself does not.

### Open judgement calls

1. **Disabled rows reachable by arrows.** Base UI and FF both let the highlight land on a disabled row (FF's test asserts it); skipping them, as the port does, is arguably friendlier and is what the port's `moveIndex` supports. Source says match Base UI; FF's test says match Base UI; flagged as a gap but a deliberate difference is defensible.
2. **Opening on mouse-down vs click.** Matching Base UI means a press-and-hold-then-drag onto an item can pick it. Cheap to do, but it needs the row `onMouseUp` hack above; decide whether the drag-release path is worth it (it changes nothing for plain clicks).
3. **Safe polygon vs dwell timer.** Bounds are fresh and the hover chain is in place, so neither blocks a geometric triangle test any more. What does: the pointer crosses the gap between the parent popup and the submenu over no element that listens for `mousemove`, and gpuix delivers `window` / `document` `mousemove` only over such an element (FORK.md:292, probe). The dwell timer stays.
4. **Focus return needs the trigger's id.** `DropdownTrigger` is a function child, so the port never holds the trigger element; saving `getFocusedElementId()` at open assumes the trigger had focus when the menu opened (true for keyboard opens and for focusable `Button`s on click, not for a non-focusable trigger).
5. **`aria-selected` as the checked state.** It is the only checked-ish state gpuix can emit, but it announces as "selected" not "checked", and Base UI itself uses `aria-selected` for the highlighted item (webkit only, `UMI:68`). Leave until gpuix wires `aria_toggled`.
6. **Hover-opened submenu: who owns the keys.** Base UI keeps arrows on the parent until Right; the port's current behaviour (arrows go straight to the submenu) is faster but differs. Fixing it also means the submenu's `litBy` first-row highlight must fire when Right enters an already-open sub.
7. **FF `size="compact"`, `className` and the gap click** are FF-owned styling/behaviour layers on top of Menu, already listed as not ported in the README; not counted here.

### FF-vs-Base-UI conflicts
- `modal={false}` (Base UI default `true`) and `alignItemWithTrigger={false}` (default `true`): FF shows a non-modal popup below/above the trigger, never the macOS-style overlay. Port matches FF.
- Pick closes 300 ms late (`selectionAckMs`, `select.tsx:54,174-192`); Base UI closes on `item-press` immediately. Port matches FF.
- Popup stays mounted through an exit spring via `preventUnmountOnClose` + `actionsRef.unmount`; Base UI unmounts on `transitionend`. Port approximates with a timer.
- Disabled rows get `pointer-events-none` and are skipped by fluid hover (`isDisabledRow`), while Base UI makes them keyboard-focusable. FF does not override the keyboard side (see judgement call 1).
- Pointer highlight is the fluid-hover nearest row (also in gaps), not the hovered `Item`; Base UI only highlights the hovered item.
- FF draws a keyboard focus ring on Select rows but explicitly none on Combobox rows (`combobox.tsx:943-945`).
- Group labels/separators are not the primitive's parts, so Base UI's group semantics are not in play.

### Open judgement calls
1. Disabled rows in arrow navigation: Base UI (and so FF) lands on them; the port, like a native `<select>`, skips them. FF does not override this, so parity says visit, but a dimmed `pointer-events-none` row taking the highlight may be unintended. Needs a decision before changing `move`.
2. Focus return: settled by F3. Rows take real focus, so a close returns it to the trigger when it sat in the popup or nowhere (`returnFocus`), and leaves a control that took it since alone.
3. Closing when focus leaves the trigger by other means (Base UI `focusOut`): the port closes on Tab and outside press only. gpuix now dispatches blur before focus (host.ts:1010), so a blur handler no longer risks the old focus-order bug (new row's focus before old row's blur).
4. `selected()` throws for a value that has no item (`select.tsx:178`); Base UI echoes the raw value. The throw matches the repo's no-fake-values rule, so left alone.
5. Popup width: settled by 6f531e6. The card has `minWidth: "anchor-size(width)"` inside `<anchored>` (`src/lib/popup.tsx:94`).
6. Mouse-down vs click open: moving to mouse-down is closer to Base UI but changes when the ack/hover starts; harmless either way.

### FF-vs-Base-UI conflicts
- `autoHighlight="always"` (cast around the types, `combobox.tsx:378`; Base UI default is `false`): the first row is highlighted on open and follows the query. That also makes `allowEscape` false, so arrows wrap row-to-row and never return to the input. The port matches (F6): first row lit on open (the picked row if any), arrows wrap, focus never leaves the input.
- Pick closes immediately (no ack delay, unlike Select); popup mount is held for the exit spring.
- `clearable` defaults to false and the Clear part is optional in Base UI; FF reserves its slot only when set. The port always renders it.
- Hover background follows only keyboard/auto highlights; pointer highlights are the fluid-hover nearest row (`combobox.tsx:943-951`); no focus ring on Combobox rows, unlike Select.
- `value` is `""` for none (Base UI `null`); `modal={false}` (Base UI Combobox default is also `false`).
- FF's `ComboboxTrigger` is `tabIndex={-1}`, which is already the Base UI default when the input is outside the popup.

### Open judgement calls
1. IME composition: Base UI holds a composing value and defers filtering (`ComboboxInput.tsx:100-102,223-287`). Whether the gpuix `<input>` reports composition updates as `onChange` mid-composition cannot be told from the types; test with an IME before porting anything.
2. Reverting the typed text on close: Base UI does it after the popup unmounts (frozen `closeQuery` keeps the list stable during exit, `AriaCombobox.tsx:800-831`); the port does it immediately at `combobox.tsx:134` while the exit fade shows the old filter. Visually minor, left.
3. Pointer-leave refilling row 0 follows from reading the `autoHighlight="always"` effect (`AriaCombobox.tsx:1198-1207`) together with `resetOnPointerLeave`; I did not run FF to confirm it is visible. Verify in a browser before changing.
4. Popup `side` / `align` / `sideOffset` props exist on FF's `ComboboxContent` but no docs demo uses them; the port hardcodes bottom/start/6.
5. Clear slot: FF reserves the 24px slot only when `clearable`; the port reserves it always. Dropping the slot also changes the field's text width relative to the screenshot in the README.

## Shared libs (`src/lib/popup.tsx`, `list-nav.ts`, `presence.ts`)

- `moveIndex` (`list-nav.ts:10-28`) already supports `wrap` and `isDisabled`; the Select and Combobox call sites were fixed in f4e2f16 and efb9663. From `null`, ArrowUp lands on the last row and ArrowDown on the first, matching both primitives.
- `revealRow` (`list-nav.ts:41-72`) is the correct workaround for the gpuix `scrollIntoView` limitation; the Combobox keyboard highlight goes through it (`combobox.tsx:277`).
- `PopupSurface` (`popup.tsx:47-112`): an `<anchored fit="flip" snapMargin={5}>` layer under its parent. `onPlacement` reports the side (the slide direction) and `availableHeight` (the card's `maxHeight`), the card has `minWidth: "anchor-size(width)"`, and a `DismissableLayer` joins gpuix's stack only while the popup is open (`:67-70`), so a second Escape during the exit reaches the dialog behind. The card's `onMotionComplete` releases the unmount when the exit ends. Its colour is `surface(min(substrate + 2, 8))` (`src/lib/surface-context.ts`), and it provides that level to its children.
- `createPlacementState` (`popup.tsx:22-36`) holds what `onPlacement` reports; it replaced `placePopup`, which measured the trigger once at open. The tooltip and the dropdown submenu use it too.
- `createPresence` (`presence.ts:11-44`): `hide()` followed by `show()` inside the 60 ms window correctly cancels the unmount, so a quick reopen during exit is safe.

### FF-vs-Base-UI conflicts

- Defaults: FF opens after 200 ms and groups for 300 ms (`tooltip.tsx:43, :67`); Base UI is 600 / 400. The port follows FF.
- `followCursor` is FF's own (`:205-219`); it is not Base UI's `trackCursorAxis`. FF wins. Base UI's `trackCursorAxis` would also make the popup non-hoverable only for `'both'`; FF's version leaves it hoverable.
- FF docs say `delayDuration` is "Milliseconds to wait before showing the tooltip on hover" (`app/docs/tooltip/page.tsx:89`). Base UI waits for the pointer to rest for that long, not just to have entered. The docs are looser than the behaviour; the behaviour is what the first table row compares.
- FF's `Tooltip` has a `TooltipPortalContainer`, `className` and `contentClassName`: web-only, n/a in the port.

### Open judgement calls

- Settled by DECISIONS.md (`f6d7b7a`): the tooltip joins the dismiss stack, closing it before the dialog behind; deliberate deviation. Original note: Escape with a hover-open tooltip above a dialog: Base UI's dialog and tooltip are separate document-level listeners with no tree link (`utils/popups/popupStoreUtils.ts:77`), so one Escape likely closes both. Joining gpuix's dismiss-layer stack closes only the tooltip first. Which is wanted? I left the stack out of the proposed fix's reach by flagging it; if "both" is wanted, the layer must not consume the key.
- Whether the hoverable-popup grace timer is worth its hit-test cost: a hit-testable box no longer blocks its ancestors' hover (FORK.md:348-349), and FF's chips are small and non-interactive.
- Per-instance fallback group in FF (`tooltip.tsx:307-316`) is a Base UI `Provider` with no `timeout`, so Base UI's default 400 applies; the proposed `skipDelay: 400` rests on that reading.

### FF-vs-Base-UI conflicts

- Touch: FF replaces the whole Base UI tree with a native-overflow `div` (`role="group"`, `tabIndex=0`) on touch-primary devices (`scroll-area.tsx:49-75`). FF shows the native one; the port shows the Base UI-style one, since it has no touch.
- FF's edge fade and divider do not use Base UI's overflow-edge attributes or CSS variables at all; they run on a CSS scroll timeline over the viewport. The Base UI edge API is unused, so it is not in the port's scope.
- FF's thumb and track sizes (`w-2.5` track, `w-1` thumb with `my-1`, `-translate-x-0.5`) set the thumb-length maths: thumb margins 8 px are subtracted (`Viewport:196-199`). The port's constants copy those.

### Open judgement calls

- Settled by DECISIONS.md (`ad68907`): the port follows Base UI's formula exactly (about 8 px low). Original note: track-click centring: Base UI computes `clickPosition = y − trackTop − thumb/2 − padding + margin/2` (`Bar:122-123`) and uses it as the thumb's offset from its margin start. With FF's 8 px of thumb margin that puts the thumb centre about 8 px below the pointer; the port centres exactly (`along − 4 − length/2`). I could not tell whether `+ margin/2` is intended or a sign slip. Keep exact centring unless the original is wanted bit for bit.
- Pressing the scrollbar: Base UI prevents default on mouse down so a focused input keeps focus (`Bar:150-153`). I marked it ported from reading `renderer.rs:5820-5836` (no focus call) but did not run it with a focused input.
- Both-axis thumb length: Base UI's `min(scrollbar.offsetHeight − cornerOffset, view − margins)` (`Viewport:199-204`) can pick the track height without subtracting the 8 px thumb margins; the port always subtracts them. At most a few pixels of thumb length; ignored.
- The port reads `view` and `content` from `onLayout`, which reports the border box. The root's border is on the outer box, not the viewport, so the viewport's border box is its padding box.
